# WP Subscriber Sync — wire protocol (v1)

This document is the contract between the WordPress plugin
[Subscriber Sync for phpList](https://github.com/albertosantambrogio/subscriber-sync-for-phplist)
(the **client**) and this phpList plugin (the **server**).
Both sides must implement exactly what is written here; any change bumps the
protocol version.

## Endpoint

The server exposes a single public page of the phpList plugin:

```
POST https://<phplist-host>/lists/?pi=WpSubscriberSync&p=endpoint
Content-Type: application/json
```

Only `POST` is accepted. Any other method returns `405`.
HTTPS is required in production; the server refuses plain HTTP unless
`WPSS_ALLOW_HTTP` is explicitly enabled (for local development only).

## Keys

Each WordPress site gets its own **key**, created by the phpList administrator
on the plugin's admin page. A key has:

| Field            | Meaning                                                                 |
|------------------|-------------------------------------------------------------------------|
| `key_id`         | Public identifier, sent in clear (e.g. `wpss_7f3a9c21`).                |
| `secret`         | 32+ random bytes, shown once, used for HMAC. Never sent over the wire.  |
| `label`          | Free text (usually the site URL).                                       |
| `allowed_lists`  | List IDs this key may write to. Any other list is refused.              |
| `default_lists`  | Lists used when the request does not name any.                          |
| `confirm_policy` | `confirmed` (subscriber is confirmed immediately) or `unconfirmed`.     |
| `allowed_attrs`  | phpList attributes this key may set. Others are ignored.                |
| `rate_limit`     | Max requests per minute (default 60).                                   |
| `active`         | Disabled keys get `401`.                                                |

The confirm policy lives **on the server**, not in the request: a compromised
WordPress site cannot force-confirm addresses or write to other lists.

## Authentication

Every request carries three headers:

```
X-WPSS-Key:        <key_id>
X-WPSS-Timestamp:  <unix time, seconds>
X-WPSS-Signature:  <hex HMAC-SHA256>
```

The signature is computed over the timestamp, a newline, and the **raw** body:

```
signature = hex( HMAC_SHA256( secret, timestamp + "\n" + raw_body ) )
```

The server:

1. looks up `key_id` (unknown or inactive → `401`);
2. refuses timestamps more than **300 seconds** away from its clock (→ `401`);
3. compares signatures with a constant-time comparison (→ `401`);
4. refuses a `request_id` already seen for this key in the last 24 hours
   **unless** it is a retry of the same body, in which case it returns the
   stored response (idempotency, see below).

## Request body

```json
{
  "protocol": 1,
  "action": "subscribe",
  "request_id": "0b6c0f0e-6a53-4b8e-9d0c-8f1f2a7f8c11",
  "site": "https://www.example.org",
  "email": "mario.rossi@example.org",
  "lists": [12],
  "attributes": {
    "first_name": "Mario",
    "last_name": "Rossi"
  }
}
```

| Field        | Required | Notes                                                                   |
|--------------|----------|-------------------------------------------------------------------------|
| `protocol`   | yes      | Must be `1`.                                                            |
| `action`     | yes      | `subscribe` or `ping`.                                                  |
| `request_id` | yes      | UUID generated by the client, **reused on retries** of the same job.    |
| `site`       | yes      | Informational, stored in the server log.                                |
| `email`      | subscribe| Trimmed and lower-cased by the server; invalid → `400`.                 |
| `lists`      | no       | Subset of `allowed_lists`. Omitted/empty → `default_lists`.             |
| `attributes` | no       | phpList attribute name (case-insensitive) → value. See below.           |

### `ping`

Used by the "Test connection" button. Needs only `protocol`, `action`,
`request_id`, `site`. Returns the lists the key may use, so the WordPress
settings page can offer them in a drop-down:

```json
{
  "status": "ok",
  "protocol": 1,
  "server": "phpList 3.7.0 / WpSubscriberSync 0.1.0",
  "confirm_policy": "confirmed",
  "lists": [ { "id": 12, "name": "Registered users" } ],
  "attributes": [ { "name": "First Name", "type": "textline" } ]
}
```

Each list also carries `"default": true|false`.

### `subscribe`

Server behaviour, in order:

1. If the address is on the phpList **blacklist** (the person unsubscribed
   earlier), do **not** subscribe and do not remove it from the blacklist.
   Return `status: "blacklisted"`. Registering on a website must never
   override an explicit unsubscribe.
2. Find the subscriber by email, or create it (`created: true`).
3. Apply `confirm_policy`. An existing confirmed subscriber is never
   downgraded to unconfirmed.
4. Set the allowed attributes (empty strings are ignored, never used to wipe
   existing values). Supported phpList attribute types:

   | type                           | value sent                          | stored as            |
   |--------------------------------|-------------------------------------|----------------------|
   | textline, textarea, hidden     | any string (max 1000 characters)    | the string           |
   | date                           | `YYYY-MM-DD`                        | the date             |
   | checkbox                       | `1`, `on`, `yes`, `true`, `sì`, JSON `true` | `on`         |
   | select, radio                  | the option **label** (e.g. `Medico`)| the option id        |

   Select/radio options are never created: an unknown label is ignored.
   Attributes that are not allowed, of another type or with an invalid value
   are listed in `ignored_attributes` and do not make the request fail.
5. Add the subscriber to the requested lists (already a member → no-op).

Response:

```json
{
  "status": "subscribed",
  "subscriber_id": 4711,
  "created": true,
  "confirmed": true,
  "lists": [12],
  "lists_added": [12],
  "ignored_attributes": ["Birthday"]
}
```

`lists_added` contains only the lists the subscriber was not already a member
of; `ignored_attributes` is present only when something was ignored.

A blacklisted address answers
`{ "status": "blacklisted", "subscriber_id": 4711 }` (`null` when the address
is only on the blacklist table).

## Status codes

| HTTP | `status` / `error`      | Client should                                  |
|------|-------------------------|------------------------------------------------|
| 200  | `subscribed`            | mark job done                                  |
| 200  | `blacklisted`           | mark job done (not an error), log it           |
| 200  | `ok` (ping)             | —                                              |
| 400  | `invalid_request`       | mark job failed, **do not retry**              |
| 401  | `unauthorized`          | mark job failed, do not retry, alert the admin |
| 403  | `list_not_allowed`      | mark job failed, do not retry                  |
| 403  | `https_required`        | do not retry, alert the admin                  |
| 409  | `request_id_reused`     | client bug: mark job failed, do not retry      |
| 405  | `method_not_allowed`    | do not retry                                   |
| 429  | `rate_limited`          | retry, honouring `Retry-After`                 |
| 5xx  | `server_error`          | retry with back-off                            |
| —    | timeout / network error | retry with back-off                            |

Error bodies always look like:

```json
{ "status": "error", "error": "list_not_allowed", "message": "List 7 is not allowed for this key" }
```

## Idempotency and retries

The client reuses the same `request_id` (and the same body) when it retries a
job. The server stores `(key_id, request_id, body hash, response)` for 24 hours:
a retry returns the stored response with `"replayed": true`, so a timeout after
a successful write never produces a duplicate. The same `request_id` with a
different body gets `409`. 5xx responses are not stored, so a retry after a
server error runs again.

The rate limit counts every authenticated request of the key in the last 60
seconds, including the ones refused with `429`.

Client back-off: 1 min, 5 min, 30 min, 2 h, 12 h, then give up and mark the
job failed.

## Data minimisation

The server logs `key_id`, `site`, `request_id`, email, outcome and time.
It never logs the signature or the raw body. Log retention is configurable
(default 90 days).
